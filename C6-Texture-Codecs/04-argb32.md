# C6.4 — Uncompressed ARGB32

> **The one-sentence version:** format `0x15` is `D3DFMT_A8R8G8B8` — four bytes per texel, one row after
> another, stored **B, G, R, A** in memory — so decoding is a swizzle, not a codec, and the only real trap
> is the channel order.

## The layout

ARGB32 is the honest, uncompressed format: every texel is four bytes, texels run left-to-right, rows run
top-to-bottom, and there is no block structure and no interpolation. A level is simply `width × height × 4`
bytes. The worked pack's `MW_LOGO` is the canonical example: 512×128 ARGB32 → 512·128·4 = **262 144** bytes,
exactly its `total_size` ([C5.4](../C5-Textures-TPK/04-finding-pixels.md)), with no mips.

The subtlety is entirely in **which byte is which channel**. `D3DFMT_A8R8G8B8` names the channels from the
most-significant bit of a 32-bit little-endian word: `A` in bits 24–31, `R` in 16–23, `G` in 8–15, `B` in
0–7. Because the word is little-endian, the **bytes** in memory come out in the opposite order:

```
byte:   +0   +1   +2   +3
channel: B    G    R    A
```

So an `A8R8G8B8` surface is physically **BGRA** in the file. Read it as RGBA and every red and blue swap —
the classic "why is the sky orange" bug.

## Decoding

```python
def decode_argb32(w, h, data):
    img = new_rgba(w, h)
    p = 0
    for y in range(h):
        for x in range(w):
            b, g, r, a = data[p], data[p+1], data[p+2], data[p+3]
            img[y][x] = (r, g, b, a)     # swizzle BGRA → RGBA
            p += 4
    return img
```

That is the whole codec. There is no endpoint math, no selectors, no mode bit. If a tool shows the image
with swapped red/blue, it read the bytes as RGBA instead of BGRA; if alpha looks inverted, it treated the
`+3` byte as opacity's complement — both are channel-order mistakes, not decode errors.

## Rows, pitch, and padding

MW's ARGB32 surfaces are tightly packed: the pitch (bytes per row) is exactly `width × 4`, with no
per-row padding. That is true because the container stores the raw surface without a D3D "locked pitch"
alignment. When you *write* an edited ARGB32 texture back, keep it tightly packed the same way — do not
introduce row padding, or every row after the first shifts and the image shears.

## When ARGB32 is the right choice

ARGB32 costs 4× a DXT texture, so the pipeline reserves it for cases where compression artifacts are
unacceptable or the data is not really "color":

- **Logos, fonts, and UI art** that must be pixel-exact — `MW_LOGO`, `FONT_MW_BODY` sits in DXT3 but crisp
  logo work often stays ARGB.
- **Lookup / gradient textures** used by shaders, where DXT's block quantisation would corrupt the values.
- **Small textures** where the 4× size penalty is negligible in absolute terms.

If you are replacing an ARGB32 texture with art that would tolerate compression, you *can* switch it to DXT
— but that changes the format tag and the byte size, so it becomes a repack, not an in-place edit
([C5.5](../C5-Textures-TPK/05-extract-replace.md)), and you must update comp-info `+0x14` to the new FourCC.

> ✅ *Verified:* `0x15` = `D3DFMT_A8R8G8B8`; `MW_LOGO` (512×128) is 262 144 bytes = `w·h·4` with no mips,
> confirming the tight 4-byte-per-texel, no-padding layout.

### Key takeaways

- ARGB32 (`0x15`) is `w·h·4` bytes per level, tightly packed, no blocks, no interpolation.
- Bytes are physically **B, G, R, A** (little-endian `A8R8G8B8`) — swizzle to RGBA when decoding.
- Pitch is exactly `w·4`; keep it tight on write or rows shear.
- Reserved for pixel-exact art, shader lookups, and small textures where 4× size is acceptable.
- Converting ARGB↔DXT changes the format tag and size — that is a repack, not an in-place swap.
