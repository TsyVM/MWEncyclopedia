# C6.5 — Palettized P8

> **The one-sentence version:** format `0x29` is `D3DFMT_P8` — one 8-bit palette index per texel, so the
> base level is exactly `width × height` bytes (verified) — but the 256-entry color table is resolved by the
> engine at load time rather than sitting in the comp-info record, so P8 is the one format where the
> container alone does not hand you finished color.

## The index data (fully verified)

P8 stores, per texel, a single byte that is an **index into a 256-color palette**. The pixel data is
therefore one byte per texel, and the base level is exactly `width × height` bytes. This is confirmed on
real data: in `GLOBALB.BUN`, the P8 texture `TREAD` is 128×64 and its base level is 8192 bytes = 128·64
exactly, with the remainder of its slice being the mip chain (each mip a quarter of the previous, one byte
per texel).

```python
def decode_p8_indices(w, h, data):
    # base level: one index byte per texel, row-major, tightly packed
    return [[data[y*w + x] for x in range(w)] for y in range(h)]
```

So the *structure* of P8 is unambiguous and matches D3D's `P8`: `w·h` index bytes, then a mip chain sized
the same way. Everything about locating and sizing P8 pixels follows the same rules as every other format
([C5.4](../C5-Textures-TPK/04-finding-pixels.md), [C6.6](06-mip-chains.md)).

## The palette (engine-resolved)

To turn indices into color you need the 256-entry palette. Here is the honest state of what the file gives
you, established by inspection rather than assumed:

- The **comp-info record carries no inline palette** — its 32 bytes are the format tag plus constants and
  zeros ([C6.1](01-format-field.md)); the word that would hold a palette pointer is **zero on disk**, the
  hallmark of a field the loader fills in at runtime.
- There is **no separate palette chunk** in the TPK: a P8-bearing pack's Info half contains only the header,
  hash table, entry table, and comp-info — no 1024-byte (256×4) palette table alongside them.
- The P8 index slices are **contiguous** with neighbouring textures (no consistent per-texture 1024-byte
  gap), so the palette is not simply prepended or appended to each texture's index block.

Put together, this means the palette for a P8 texture is **supplied by the engine at load time** — the
on-disk record is an index image plus a runtime-populated palette handle, not a self-contained indexed
image. The container gives you the indices; it does not, by itself, give you the colors.

> ✅ *Verified:* P8 = `w·h` index bytes; base size matches `w·h` exactly (`TREAD` 128×64 → 8192). Comp-info
> holds no inline palette and the TPK holds no palette chunk; the palette pointer is zeroed on disk.
> 🟡 *Open (honestly):* the exact provenance of each P8 palette at runtime is engine-internal and not
> recoverable from the pack alone. P8 is a rare format (58 textures game-wide) used for small indexed art,
> so this gap affects very little.

## Working with P8 in practice

Because P8 is a tiny minority and its palette is engine-side, the pragmatic guidance is:

- **To view a P8 texture faithfully, you need the runtime palette.** From the file alone you can render the
  *index* image (a grayscale-like map of 0–255) and its structure, but not its true colors, unless you
  obtain the palette the engine uses for it.
- **To replace a P8 texture, prefer keeping it P8 with the same dimensions** so the index byte count is
  unchanged and the edit stays in-place ([C5.5](../C5-Textures-TPK/05-extract-replace.md)) — you are editing
  which palette entry each texel points at, not the colors themselves.
- **If you need full control over color, convert the texture to an uncompressed or DXT format** and update
  comp-info `+0x14` accordingly. That makes the texture self-contained (no external palette) at the cost of a
  repack and a larger footprint. For the small HUD/sprite art P8 is used for, converting to DXT3 or ARGB32 is
  usually the cleanest path for a modder who wants predictable results.

## Why P8 exists here at all

P8 is a legacy-efficient format: one byte per texel with a shared 256-color table is very compact for art
with a limited palette (icons, simple sprites, indexed effects). On the hardware MW targeted, an
engine-managed palette was cheap, and for small indexed images P8 beat both ARGB32 (4×) and DXT (which would
quantise an already-limited palette). Its rarity in the shipped data shows the pipeline treated it as a
niche tool, not a default.

### Key takeaways

- P8 (`0x29`, `D3DFMT_P8`) is one 8-bit palette index per texel; base level = `w·h` bytes (verified on
  `TREAD`, 128×64 → 8192).
- The palette is **not** in comp-info and **not** a TPK chunk — the on-disk palette pointer is zeroed and
  the engine resolves it at load time.
- From the file you can recover P8 *indices and structure* but not true colors without the runtime palette.
- Replace P8-with-P8 for in-place edits; convert to DXT3/ARGB32 when you need self-contained, predictable
  color.
- P8 is a rare niche format (58 textures game-wide) for small indexed art.
